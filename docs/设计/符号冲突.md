# 包间符号冲突问题

C++项目的包管理器一点比较复杂的部分是不同包间可能存在符号冲突，导致应用程序无法正常链接。比如一种典型的情况就是两个包都定义了用于字符串拼接的join函数，并且函数签名相同也都没有通过命名空间包裹，链接时就会导致多重符号定义错误。

# 解决方案

Cup的解决方案是伪命名空间，伪命名空间是一个以`$`开头的标识符，例如`$pkg`，采用`$`开头是为了尽可能不与现有代码中任何标识符重复，便于迁移，伪命名空间名称的用法与命名空间名称相同，它的存在只是为了在编译项目时为每个包生成一个唯一的域名，避免不同包间的符号冲突。

伪命名空间本质上是一个宏定义，通过特殊的规则在构建时生成一个构建时全局唯一的命名空间名称，并替换掉其对应的伪命名空间名

同时，伪命名空间还保留了一个`$pkg`用于指代当前包的伪命名空间

## 包唯一标识生成

构建项目时，任何一个包都必然对应一条唯一的访问路径，将包中的Cup.toml所在的访问路径作为一个唯一标识源，以它生成一段MD5作为唯一校验后缀，同时将包名作为前缀，生成一个实际的命名空间名称

```cpp
#define $fs fs_dd078bbd713758bb // 由cup生成宏替换表，$fs可能的替换值

using namespace $fs;

// 上面宏展开后变成
using namespace fs_dd078bbd713758bb;
```

## 外部依赖项访问

当你在Cup.toml文件中引入外部依赖项时，你可以指定它的名称，比如：
```toml
[dependencies]
fs = { git = "owner/fs-lib", tag = "v1.0.0" }
```
依赖项中的键名（此例中的`fs`）就决定了这个库伪命名空间在你包中的访问方式，你可以通过`$fs`来访问它，这个名称中包含的任何无法作为C++标识符的字符都将被替换成`_`

## 备注

伪命名空间机制作为 Cup 的一种解决链接符号冲突问题的方案，应当在编写包时遵循：除宏指令以外所有的包代码都应该被包含在`namespace $pkg {}`之中，但它并非强制要求，如果你的包不用于发布到网络供他人使用或者你的包无法作为依赖项使用（例如可执行文件和模块库）则可忽略此规则
